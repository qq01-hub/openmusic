# 微信与 QQ 扫码登录

## 后台配置

1. 打开管理后台的「系统设置 → 第三方服务 → 接口盒子」，填写并保存自己的用户 ID 与 API Key
2. API 地址使用 `https://cn.apihz.cn/api` 或 `https://vip.apihz.cn/api`，登录请求仅向这两个官方 HTTPS 地址发送凭据，不使用文档中的明文 HTTP IP 线路
3. 在「系统设置 → 身份登录 → 微信与 QQ 扫码登录」分别开启需要的方式并保存，默认均关闭，无需新增环境变量或为开关重启服务
4. 在管理员账号与密码设置中的扫码登录区域，扫描自己的二维码完成管理员绑定

两个开关同时控制前台与后台对应的扫码登录，接口盒子 ID 和密钥与现有表情包服务共用，关闭开关会阻止新的扫码及尚未完成的扫码流程，已有绑定和已经签发的本站会话保留

## 登录与绑定

- 登录列表中的微信扫码登录排第一、QQ扫码登录排第二，原微信登录展示为微信文件传输助手登录
- 聚合微信保存为 `wechat_scan`，QQ 保存为 `qq_scan`，旧文件传输助手继续使用 `wechat` 与原有 UIN 索引
- 不按昵称或头像合并账户，新微信与文件传输助手不共享身份，已有用户应先登录原账户，再在账户与安全中分别绑定
- 前台绑定不会授予管理员权限，后台绑定要求已登录的管理员会话，后台扫码登录只接受已经绑定的同类型身份
- 普通账户仍执行现有身份唯一性和最后一种登录方式保护，不能将其他账户已绑定的身份抢绑过来
- 微信须在 30 秒内扫码、1 分钟内确认，本站微信流程有效期 60 秒，QQ 流程有效期 5 分钟，过期后重新获取二维码
- 页面每 2.5 秒查询一次，离开扫码界面会停止轮询，二维码刷新、账户变化、重复完成和前后台流程串用均会被拒绝

服务端通过 `jhdl.php` 发起、通过 `jhdlq.php` 查询服务端持有的查询编号并核验登录类型及 openid，再接入本站账户或管理员绑定

`jhdly.php` 用于接口盒子自身的账号密码映射与封禁系统，本站使用自己的账户、管理员凭据和封禁规则，不读取该接口返回的明文账号密码，也不把已知 openid 当作扫码证明

API Key、上游查询编号与完整 openid 不返回浏览器，二维码图片由服务端从限定的接口盒子 HTTPS 图片路径获取后内嵌返回，上游头像不作为身份依据

## 数据、发布与回退

新增运行时配置 `apihzWechatEnabled` 与 `apihzQqEnabled`，沿用已有运行时配置持久化与密钥加密方式，管理员绑定追加到 Redis 的 `openmusic:admin:credentials` 记录中，用户身份复用现有 Redis 账户与身份索引

临时扫码状态与限流位于 `openmusic:account:social-login:v1:`，自动过期，不需要迁移旧账户或旧微信数据，Redis 不可用时拒绝扫码，不使用内存或浏览器缓存替代身份存储

先升级并重启服务端，再发布前端资源，旧客户端忽略新增的登录方式，继续使用旧登录链路，Flutter、Android 与 iOS 桥接契约不变

验收时检查前台两个方式的排序、扫码与绑定、管理员拒绝未绑定身份、关闭开关、重复确认、账户切换、扫码过期与 Redis 故障，观察 `account_auth_total` 的成功、拒绝与上游失败计数，以及后台扫码绑定、解绑和失败审计，这些记录不构成完整告警系统

回退前先关闭两个扫码开关，备份运行时配置与 Redis，再恢复上一版配套服务端和前端，旧微信 UIN 索引保持原样，旧版若重写管理员凭据记录可能丢弃新增扫码字段，重新升级后需核对并重新绑定

发布记录应包含实际发布版本、负责人、配置开关、验收结果及回退触发条件，真实手机扫码与部署网络验收由发布环境完成
