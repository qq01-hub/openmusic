# 全项目 Redis 治理与容量边界

更新日期：2026-10-29

## 目标与实施顺序

本轮按共享连接、写入合并、原子一致性、数据留存、读取放大、可观测性及恢复顺序审查服务端 Redis 入口，不以增加内存权威缓存、取消鉴权或删除历史业务数据换取低请求量

- P0 已实施：关闭客户端离线命令积压、限制命令队列、房间快照合并与有界并发、错误上报和热榜关联数据淘汰、管理审计清理并发安全
- P1 已实施：收藏分类 CAS、设备双向索引原子更新、公共 Lua 脚本缓存、批量启动恢复、上报摘要读取、收藏分享减少重复读取及比较后撤销
- P2 需生产数据验收：按实际账户数、房间数、收藏体积、诊断快照大小、峰值并发与磁盘性能制定容量预算和告警阈值，历史孤儿正文清理需先导出备份与候选清单，经确认后执行

不承诺数据量永不增长，账户、收藏、绑定、管理员凭据和长期业务记录本来就会随业务量增长，本轮处理的是可避免的重复写、过期明细残留、无界命令积压和读取放大

## 连接与背压

共享连接设置 `disableOfflineQueue: true`、`commandsQueueMaxLength: 4096` 和五秒单次连接超时，断线时非幂等操作不会在客户端离线队列中长期堆积并于重连时集中执行，队列满时应进入已有失败路径，而不是无限占用内存

初始化采用 single-flight，首次连接重试有明确上限，已成功连接过的实例断线后采用带抖动的指数退避继续恢复，退避上限约五秒，安装探测连接使用八秒超时且不自动重连，避免错误地址使安装接口长期悬挂

这些是每个进程的边界，不等于全站总并发限制，也不是 Redis 容量保证，生产需要继续关注拒绝量和超时，不应通过把队列上限无限增大掩盖饱和

## 房间写入

`coalescedRoomWrites.js` 只合并可由最新版本替代的房间完整快照，不能用于收藏增删、计数、令牌消费或鉴权

- 空闲时使用 100 ms 合并窗口，繁忙写入持续排空，每个房间最多一个在途快照和一个最新待写快照
- 后台同时最多写八个房间，不将每次房间更新变成无限 Promise 链
- 普通保存把正文与索引合为一批事务，初始化密码迁移也按八个房间分批写入
- 删除房间前取消待写快照，已进入同房间串行队列的写入先结束，再删除，避免旧快照复活已销毁房间
- 写入失败保留最新快照，延迟重试，不立即循环冲击 Redis，显式 flush 等待其他在途写结束后报告失败
- 退出 flush 跳过合并计时器，并覆盖房间管理层与底层写队列，不因上层队列已空而漏掉在途任务

仍沿用现有房间内存状态机和异步持久化契约，进程突然崩溃或 Redis 持续不可用时不承诺零丢失，不声称已经实现多实例房间强一致或持久化 WAL

## 数据留存与读取

### 热榜

排名与元数据在同一脚本内更新和淘汰，常态各不超过 200 项，修复只删除排名成员而让元数据长期增长的问题，兼容的内存展示兜底同样限为 200 项

旧元数据使用 HSCAN 游标分批整理，按每次最多 100 个字段原子复核是否仍在榜，仅删除不在榜的派生元数据，超量扫描页留待下次处理，COUNT 是 Redis 扫描提示而非绝对硬上限，写入脚本及后台清扫处理历史超额排名时每次最多删除 200 个成员

### 错误上报

保留最近 100 条的既有策略，新写入造成淘汰时原子移除 ID、正文和摘要，正文使用 UNLINK 异步释放，修复只裁剪 ID 而遗留大正文键的问题

新增 `openmusic:error_reports:summaries` 是 Redis 中的派生列表视图，写正文时同时写摘要，正常列表为 LRANGE 加 HMGET，旧记录缺失摘要时每批最多 MGET 20 个正文并补齐，补齐前原子检查 ID 仍在当前列表且使用 HSETNX，不覆盖并发的新摘要

2026-10-29 增加后台增量清扫，旧版本遗留且不在最近 100 条 ID 索引内的报告正文，仅在能解析出匹配的报告 ID、创建时间已超过 24 小时且正文不超过 256 KiB 时回收；删除前在 Lua 内重新检查当前引用，再通过 UNLINK 释放正文并删除摘要

最近 100 条报告即使较旧仍保留，24 小时宽限期按正文创建时间计算，无法解析、时间缺失或超大正文保留供人工核查，自动清扫不会按 Redis 总 key 数任意删除业务数据

### 播放历史与后台清扫

播放历史不是逐首创建 Redis key，而是包含在 `openmusic:room:<房间号>` 的 JSON 快照中，最多保留最近 150 条；漫游去重记录最多保存 200 条，与可查看的播放历史分开处理

私人漫游当前音源去重达到 200 首时，按最早到最近的顺序释放最久远的记录至 199 条，当前曲始终保留，随后逐首滚动淘汰；重复播放会刷新该曲在去重记录中的位置，QQ 推荐批次无新歌时仅选择其中最久远且不是当前曲的一首兜底，不整批重播近期歌曲

快照写入和恢复均限制漫游去重记录为 200 条，启动时发现旧房间播放历史、漫游去重或聊天记录超额，会按现有快照上限分批重写；房间、凭据和快照格式保持兼容，无需清空 Redis 或重建房间

`redisMaintenance.js` 在服务启动后执行一次，此后每分钟增量处理，单实例只允许一个在途清扫，正常退出先停定时器并等待本轮完成

- 报告正文每轮最多复核 50 个候选，孤儿摘要每轮最多处理 50 个字段，超量扫描结果留待下一轮
- 全局房间索引每轮最多复核 50 个成员，账户房间索引每轮最多处理五批，每批 50 个成员；仅删除对应房间 key 不存在的索引成员，内存中仍有房间的记录跳过，不删除房间正文
- 热榜每轮最多淘汰 200 个超额排名及其元数据，再复核最多 100 个元数据字段，排名和元数据删除均在 Lua 内复核
- 使用 SCAN、SSCAN、HSCAN 游标推进，不使用 KEYS、FLUSHDB 或 FLUSHALL，COUNT 只是扫描提示，删除数量由独立批量上限控制
- 收藏、账户、设备身份、管理员凭据、封禁和通知不在自动清扫白名单内，既有空房超时销毁和短期业务键 TTL 继续生效

清扫记录 `redis_maintenance_runs_total`、按类别区分的 `redis_maintenance_removed_total`，失败计入 `redis_error_total` 的 `maintenance` phase，只有实际移除数据时输出数量日志，不输出报告正文、账号信息或凭据

上线前备份 Redis，更新并重启服务端即可启用，无需新增环境变量、修改后台配置或刷新前端；回滚程序会停止新增清扫，已删除的旧孤儿报告正文和超额历史只能从备份恢复，仍被引用的数据不应被清扫

### 审计

不再执行「客户端 LRANGE 全表 → DEL → RPUSH」重建，避免抹掉并发 LPUSH 的新审计，每批仅原子检查并移除列表尾部最多 200 个过期或无效记录，仍有待清理数据时缩短下一批等待

列表按新到旧写入，接口继续按时间过滤，服务器时钟严重倒退造成的中间乱序旧记录可能暂留到数量裁剪或整个键到期，不把尾部清理描述为全量时间排序修复

### 收藏与身份

收藏分类沿用旧 JSON 格式，以 Redis CAS 重试处理并发，读取失败或非数组、损坏 JSON 不当作空数据覆盖，收藏内容的 CAS 若新旧 JSON 完全相同则不重复 SET，不增加本地权威缓存

分享创建复用同次操作中已经验证过的 Redis 分享快照，撤销使用比较后删除，避免读后删误删并发产生的新归属

设备换绑、反向索引和过量成员淘汰合为原子操作，正常每用户最多 20 个设备，遇到历史超大集合单次最多处理 100 个旧成员，后续操作继续收敛，权威读取仍实时验证 Redis，并保持原有 180 天续期

## 脚本调用

全部业务 EVAL 入口统一使用 `redisScripts.js`，优先 EVALSHA，仅 NOSCRIPT 时补发 EVAL，连接丢失、超时和 ACL 错误不重放非幂等操作

进程仅缓存脚本文本到 SHA 的映射，最多 128 项且总文本不超过 1 MiB，不缓存业务查询结果，账号、收藏、会话、限流的权威状态没有因此转入进程内存

需要 Redis 7 部署基线以及对应的 EVAL、EVALSHA、SSCAN、HSCAN、MGET、HMGET、LPOS、UNLINK 和事务命令权限，仓库 Docker 配置使用 Redis 7，外部托管 Redis 应在预发布验证 ACL，不通过放宽认证或关闭 TLS 解决权限问题

## 可观测性与容量验收

新增累计指标 `room_storage_coalesced_total`、`room_storage_retry_total`，沿用 `redis_error_total` 的固定 phase 标签，管理概览接口追加 `redisWriteQueue`，展示待写房间数、在途房间数和串行操作房间数，不将房间 ID 作为高基数指标标签

生产应监测 Redis used_memory、RSS、连接数、拒绝连接、命令延迟、slowlog、AOF rewrite、持久化错误与 eviction，并将待写房间数长期上升、连续写入失败、错误上报键数超过保留范围视为核查信号，现有日志与计数不等于已经部署完整监控和告警

权威账户、签名密钥、收藏和配置不应与可任意淘汰的纯缓存混用 allkeys-LRU 策略，容量不足应扩容或按明确业务规则归档，不应自动淘汰鉴权数据，本轮没有替用户修改生产 Redis 内存、AOF、持久化卷或淘汰策略

## 验证与上线

本轮使用独立的本地 Redis、独立端口和测试数据，不加载生产 Redis 连接，不对线上压测，覆盖慢存储合并、一万次同房间更新、并发上限、取消删除、失败恢复、退出等待、收藏并发与损坏保护、设备双向索引、报告摘要迁移、热榜孤儿元数据和审计并发清理

实施命令包含 `npm test --prefix server`、`npm run lint --prefix server`、Node 语法检查及 `git diff --check`，测试期间创建的临时目录在验证结束后按清理清单移除，正式测试、用户已有源码、运行配置和必要构建产物不属于清理范围

上线前备份 Redis，先预发布核对命令 ACL、慢存储背压与退出行为，再重启服务端，不需要刷新客户端或修改收藏格式，管理概览新增字段为可选追加，主站新人指引无需变化

回滚恢复程序版本，保留账户和收藏键，不重新生成密钥，已经按既有保留上限淘汰的报告正文或审计记录不能仅靠回滚程序恢复，需事前备份，回滚到不维护上报摘要的旧版本后再次升级，应重建派生 summaries 哈希，不能把旧摘要当作更新后的权威正文

## 后续容量工作，不在本轮伪装为已解决

- 账户及绑定记录随注册用户数增长，需要账户注销、保留期限和业务归档政策，不能擅自设置短 TTL
- 收藏仍为每用户单 JSON，虽然数量有限，大收藏更新仍需读写整份 JSON，进一步拆分需版本化迁移、回滚和并发协议设计
- 常驻房间通知与捐赠记录是长期业务数据，不能以 Redis 优化为理由删除未确认通知和历史记录
- 部分历史非核心模块仍有既有进程缓存或降级行为，本轮未宣称全站具备跨进程强一致，正式多实例架构需要单独设计和验收
- 未完成生产规模压测、Redis 故障切换演练或多实例验证，不能以本地专项测试承诺任意规模下绝不增长或永不故障
