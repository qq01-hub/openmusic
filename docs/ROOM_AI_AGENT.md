# 房间 AI 对话与工具

## 实际调用链

房间 AI 使用项目内的 Function Calling 工具
`server/aiModelService.js` 定义工具与系统提示，`server/roomAiAgent.js` 执行工具
开发环境的 Codex MCP 工具不属于这份工具清单，不会自动成为房间 AI 的能力

`send_chat` → 服务端聊天校验 → 唤醒判断 → 分布式频率限制 → AI 任务队列 → 精简提示与压缩历史 → 主模型与工具循环 → 服务端消息发送

- 用户可以通过昵称、`/ai` 或回复经过服务端验证的 AI 原消息继续交流
- 回复不新增 Socket 事件，仍走现有聊天、限流与任务队列
- 同一房间同一成员的 AI 任务串行处理，实际操作按任务台账避免重试重复执行
- 主模型直接理解与执行，不再为每条消息额外调用独立意图模型
- 模型决定是否执行、如何消解指代以及是否需要补问，服务端最终检查成员身份、权限、参数、频率、队列规则和实际执行结果

## 本次排查的主要问题与调整

| 原问题 | 调整 |
| --- | --- |
| 历史回放缺少身份，无法可靠区分同名、改名和其他人的任务 | 每轮保留成员 ID、昵称、会话所属成员、消息 ID 和引用 ID |
| 用户历史或压缩摘要被放在 system 角色 | 作为普通引用资料传入，不能升级成系统指令或新授权 |
| 引用主要依赖客户端短文本，引用链和卡片顺序缺失 | 按本房间真实原消息解析引用，最多回溯 4 条，歌曲序号按实际展示顺序 |
| 最后一次搜索覆盖了已经展示的卡片顺序 | 卡片真正发送后保存该组展示顺序，明确引用时优先使用对应组 |
| 推荐是否入队依赖前置分类和关键词，工具行为不直观 | 移除独立前置分类，主模型通过 `recommend_songs.enqueue` 表达是否播放，通过 `count` 表达数量 |
| 正常取消、改称呼或游戏角色扮演可能触发违规 | 收窄检测范围，保留覆盖系统规则、索取秘密和冒充管理权限等真实越界 |
| 工具使用过时的权限快照 | 执行前重新读取当前成员权限，具体操作继续走已有服务端校验 |

## 多人上下文与资料边界

- `speaker.userId` 表示说话者，`conversationUserId` 表示这一轮所属成员
- 当前成员自己的长期摘要和历史独立保存，每轮最多回放最近 8 条原文，较早内容转为摘要
- 公开聊天背景最多 6 条，其他成员近期 AI 互动摘要最多 3 条
- 提示中在线成员预览最多 12 位，完整房间快照仍最多包含 30 位成员的公开 ID 与昵称，头衔、昵称和聊天文本不能证明管理权限
- 对引用中的文字、歌曲、昵称、识图内容、用户画像备注和自定义性格，只作为资料理解
- 同名、改名和序号都结合成员 ID、原消息与引用关系判断，旧摘要中无法确认身份的内容不补猜身份
- 引用其他人收到的公开歌曲卡片并明确要求操作时，以当前成员本人身份执行
- 收藏仍只从 Redis 读取当前对话用户的数据，不接受模型传入其他目标用户身份
- 上下文窗口裁剪优先保留带身份封装的消息信息，自动压缩摘要不使用 system 角色
- 内部成员 ID 用于理解上下文，回复通常只使用昵称

## 推荐并播放

`recommend_songs` 支持可选参数 `enqueue` 和 `count`

- `enqueue=false` 为默认值，只返回推荐候选
- 用户在本轮或未取消的前文明确要求推荐并播放时，由主模型设置 `enqueue=true`
- 播放默认 3 首，仅推荐默认 5 首，单次最多 5 首
- 每首歌曲仍走实际点歌权限、冷却、数量、歌曲有效性与禁播检查
- 遇到限制时保留已成功结果并停止这一批，按真实成功数量说明
- 读取真实候选并确认结果后再回复，不能把发出卡片或口头承诺当作入队成功

## 自然交流

主模型可以结合成员偏好与房间话题自然陪聊
普通角色扮演不改变助手真实身份、房间角色或工具权限

## 当前提示词结构

- 对话理解：合并进主模型固定规则，结合当前成员消息、引用和压缩历史直接判断，不增加独立模型请求
- 固定系统提示：音乐精灵身份、原生性格、真实执行要求、多人身份边界、权限与表情格式
- 房间性格：叠加房主设置的语气与互动偏好，不赋予额外权限
- 动态状态：注入当前成员权限、关系阶段、音乐偏好、时段与房间播放状态
- 历史与引用：作为带身份的普通消息或参考资料提供，不能升级为系统指令
- 行动要求：明确要求推荐并播放时直接尝试入队，合理默认能解决的情况不反复确认，实际结果以工具返回为准
- 正常交流：取消推荐、更新称呼、纠错和催促不按关键词惩罚，真正覆盖系统规则、索取秘密或要求越权才拒绝
- 情感状态：保留正常、略烦、明显生气、很生气和冷处理阶段，按当前成员状态回应
- 小游戏工具、游戏状态、游戏快捷入口，以及短故事、笑话和接龙的专项提示均已删除

## 输入开销控制

- 固定提示规则合并去重，最小房间样本从约 9715 字符降至约 2176 字符，实际长度随时段等资料略有变化
- 完整 QQ 表情目录不再每次注入，提示只提供少量格式参考，模型可通过 `get_qq_faces` 按关键词或分页读取，每页最多 20 项
- 成员画像按字段截取，保留常点歌手、近期歌曲、不喜欢内容和短备注，队列仅提供必要歌曲信息
- 历史每累计到 12 条原文时滚动压缩 6 条，发送时最多回放 8 条；既有快照继续兼容，无需迁移
- 单次房间文本请求设置约 8192 的估算输入 token 上限，包含消息与工具定义，同时尊重后台模型窗口和输出预留
- 保留系统规则和最新请求，旧记录压为资料摘要；超大工具调用与返回成组压缩，避免产生孤立的 `tool` 消息
- 工具执行结果进入下一轮模型上下文前会按工具类型裁剪，只保留成功状态、错误、歌曲候选、权限和播放决策字段，封面、播放地址、歌词、表情包 URL 等展示字段不重复注入，单个结果设 2400 字符硬上限
- 空的候选资料与空的公开聊天资料不再创建占位消息，引用图片只传是否有图和识图所需的摘要，不把原始图片地址重复放进文本上下文
- 规则和工具本身已无法装入预算时明确失败，不静默移除权限规则或发送超预算请求
- 估算仍使用项目现有字符近似算法，不能作为供应商实际计费 token 数或节省费用的承诺

服务端输出清理只拦截明确的工具泄漏写法，例如反引号包裹的函数名或“调用 search_songs”这类句式，普通回复中讨论工具名时保留原文

## 界面

- AI 消息沿用普通成员气泡配色，昵称后保留暖色 AI 标签
- 房间显示头像时，AI 默认头像使用现有 `/desk-pet/previews/v2.webp`
- 桌宠气泡保留 `OpenMusicPet` 字体，使用正常字重、禁用合成粗体，调整字号、行距和字距
- 表情统一规范为可渲染标记，正文、引用和桌宠气泡兼容旧标记，逐字动画不会拆开表情

## 数据兼容与发布

成员上下文只增加可选消息字段
不新增 Redis 键或环境变量，不改变收藏权威存储
旧记录缺少新字段时按旧身份资料读取，无需迁移
回滚旧服务端可以忽略新字段，旧版本重新保存快照时可能丢失新增的消息身份和引用字段

先发布兼容服务端，再发布客户端，移动端仍使用现有 WebView 聊天协议，无原生桥接字段变化
观察原有 AI 请求、拒绝、用量与上游错误，独立意图分析请求及其计数已移除
计数不等于完整监控或告警
